# 第 11 章：验证面试问答与计算题

- 这 40 题配合 [README](README.md) 和 [一键回归](lab/run_all.sh) 使用。先从“一笔请求怎样被驱动、观测和核对”开始，再学随机、断言和验证框架。

- 回答时尽量给一个具体场景，例如“下游三拍不收结果怎么办”，再解释采用的检查，而不只罗列工具或英文名词。

## Testbench 与验证计划

**1. 一个最小的自检查 testbench 应包含什么？**

- 时钟/复位、合法激励、实际接口观测、参考结果、自动比较、完成条件和超时。成功不只是没有报错，还应确认在途事务排空、必测场景发生。波形用于调试，不能代替比较器。

**2. Reference model 与 scoreboard 有何区别？**

- 例如输入 5+3，reference model（参考模型）负责算出期望值 8；scoreboard（记分板）负责记下这笔期望，等实际结果返回后找到对应项并比较。

- 前者解决“应该是多少”，后者解决“这份结果该和哪份答案比”。按序模块可用队列，乱序模块则要借助 ID/tag 标明对应关系。

**3. 为什么不建议照抄 DUT 写参考模型？**

- 相同算法和控制结构可能包含同一个错误。应选择更独立的抽象，例如用整数/精确数学计算验证位级运算，用事务队列验证寄存器槽。独立模型也可能有 bug，仍需边界例题和交叉检查。

**4. 本章 monitor 为什么在上升沿读取旧 result？**

- 上升沿之前的 valid/ready/result 决定本拍实际传输。DUT 的非阻塞赋值在 NBA 更新，monitor 在此之前读取旧值，正好观察消费的旧响应。

- 若等到 NBA 以后再无条件比较，可能误读下一笔数据。

**5. 在上升沿用阻塞赋值驱动输入有什么风险？**

- 驱动和 DUT 读取可能处在同一事件区，进程执行顺序决定读取新值还是旧值。可以采用明确错开的驱动边沿，或定义 clocking block 的驱动/采样语义。随意添加延迟可能隐藏问题，不能代替时序约定。

**6. `$display`、`$strobe`、`$monitor` 怎么选？**

- `$display` 在调用时打印，适合事务与错误信息；`$strobe` 在时间片末观察更新后的值；`$monitor` 在参数变化时持续输出时间片末的值。三者都不自动判定正确性，也不应被当作 scoreboard。

**7. 为什么比较器用 `!==` 而不是 `!=`？**

- `!=` 遇到 X/Z 可能返回 X，`if(X)` 不进入真分支，从而漏报。`!==` 给出确定的 0/1，可以检测四态差异。不过期望值自身若允许 X，应明确如何比较，不能机械地将所有 X 都判定为同一种错误。

**8. 计数题：本章接受 1,707 笔，只输出 1,698 笔，是丢包吗？**

- 不一定。本章九次运行各复位取消一笔，共 9 笔，满足 `1707=1698+9`，并检查队列排空。若没有显式取消策略和取消计数，单靠少了九笔无法判断是否合法。

## SV 对象、随机与覆盖率

**9. 类句柄赋值为什么会污染 scoreboard？**

- 句柄只是找到对象的引用。把同一个句柄放进队列两次，再把对象的 a 字段从 5 改成 9，队列两项读到的可能都是 9，因为它们指向同一份内容。

- 要保留两笔不同请求，应每笔新建对象或正确复制对象，并避免发布后继续修改被其他部件使用的那一份。

**10. 继承、virtual 方法和多态分别起什么作用？**

- 继承复用并扩展基类成员；virtual 方法允许子类覆盖行为；父类句柄调用时根据实际对象类型分派。仅用父类句柄指向子类，并不意味着所有非 virtual 方法都会自动动态分派。本章子类扩展约束，没有覆盖预测方法。

- 例如基类定义 virtual 的 predict，子类重新实现它；父类类型的变量若引用这个子类对象，调用 predict 时会执行子类版本。这叫多态：同一种调用形式，按实际对象选行为。

- 它描述测试程序怎样复用代码，不是综合出硬件选择器。

**11. `randomize()` 失败后怎么办？**

- 立即报错或进入明确的恢复策略，检查约束冲突、范围、启用状态与 inline constraint。不能继续使用字段假装得到了一笔新随机事务。返回成功只说明找到了合法解，不表示覆盖率已达标。

**12. Inline constraint 会自动覆盖类约束吗？**

- 通常与启用的类约束共同生效。类要求 a≤15、inline 要求 a=31 会产生冲突。若需要不同合法域，应设计可配置约束或明确关闭相关约束，并保留测试意图。

**13. `dist` 和 `solve before` 是什么？**

- `dist` 为值或区间提供分布权重；`solve before` 指定相关变量的求解先后，可能影响联合分布。它们不应被误解为“每轮必命中边界”或“任意覆盖类约束”。实际覆盖仍需测量。

**14. Mailbox 与 semaphore 如何区分？**

- Mailbox 像收发请求的队列：生成器放一笔，driver 取一笔；空了就等新消息，容量满了就等对方取走。

- Semaphore 更像共享资源的钥匙：先拿到钥匙才能使用，用完归还，本身不装请求数据。本章只有一个 driver，演示了钥匙的获取和归还，没有验证多方竞争。

**15. 功能覆盖率和代码覆盖率为什么都需要？**

- 功能覆盖率围绕规格场景，代码覆盖率围绕实现结构。代码全部执行过可能仍漏掉重要输入组合；功能 bin 全满也可能没有覆盖隐藏分支。两者都不检查结果是否正确，必须结合断言与记分板。

**16. 计算题：三个二值 coverpoint 的 cross 有多少格？**

- 在所有组合合法且不排除 bin 时是 \(2^3=8\) 格。本章统计 op、a 是否零、b 是否零。8/8 仅代表这些格均被命中，不代表 8 位输入空间全部遍历。

**17. 计算题：某场景概率 1/8，32 次随机后一定出现吗？**

- 不一定。在独立、均匀前提下，未出现概率为 \((7/8)^{32}\)，约 1.39%。这是一个指定场景未出现的概率，不是所有八格均覆盖的概率。实际约束分布还可能不均匀。

**18. 为什么在响应完成时采样覆盖率？**

- 生成事务不等于送达或完成。响应完成采样可避免被 reset 取消、未被 DUT 接受的事务被误计为完成场景。某些需求应在请求接受或协议中间阶段采样，采样点必须与 bin 的定义一致。

## SVA

**19. 立即断言与并发断言有什么区别？**

- 立即断言在过程执行时检查当前表达式；并发断言按采样时钟表达时间关系。前者适合求解成功、当前函数结果等，后者适合握手保持、延迟与协议顺序。需要确认模拟器实际启用了断言。

**20. `|->` 与 `|=>` 差在哪一拍？**

- 先看单拍例子：A 在第 5 拍为真，`A |-> B` 检查第 5 拍的 B，`A |=> B` 检查第 6 拍的 B。

- 若 A 代表一个多拍序列，就先找序列匹配结束在哪一拍，再从那一拍或下一拍开始后件。关键是找到时间起点，而不是只背“差一拍”。

**21. 为什么输入握手到寄存响应使用 `|=>`？**

- 并发属性在上升沿采样时还没看到这个沿的 NBA 更新。本拍输入被接受后，新响应在沿后写入，下一次采样沿才能观察到它。对本章单槽电路，后件还需用 `$past` 取对应输入。

**22. 反压保持属性为何在 ready 恢复时也要检查？**

- 第 n 拍 valid=1、ready=0，原数据必须保持到第 n+1 拍的采样点，即使该拍 ready 已经为 1。只有完成这次握手之后才能更新。若只检查连续两拍 ready=0，会漏掉解除反压的边界。

**23. `disable iff` 是简单的同步 if 吗？**

- 不是。它为属性提供异步禁用/中止语义，通常用于复位取消待决检查。它与普通时钟采样前件不同，复位在采样附近变化时更需要明确调度和设计规则。

**24. 真空通过怎么发现？**

- 例如请求从未出现，`req |=> ack` 可能一直通过而没有验证响应。可检查前件触发次数，增加有意义的 cover，审查假设。

- 本章要求 launches、stalls、clears 都非零，但这不等于所有属性质量都已证明。

- 因为这条属性只说“如果有请求，下一拍应答”，没有请求就没有必须检查应答的义务。要证明测试确实考过这一题，还得确认请求出现过；属性没有失败与场景已经发生，是两份不同的证据。

**25. “请求最终完成”为什么可能无法证明？**

- 环境可以永久背压，设计就无法完成消费。需明确保证的是内部响应出现，还是外部消费完成；后者可能需要公平性或有界 ready 假设。不能为了证明通过而随意假设 DUT 已经正确。

## UVM

**26. `uvm_component` 与 `uvm_object` 如何选择？**

- 具有父子层次、参与 phase 的 driver/monitor/env 通常是 component；事务、sequence、配置通常是 object。

- Sequence 是动态激励对象，不是固定组件树中的 driver。

**27. Sequence、sequencer、driver 分别负责什么？**

- Sequence 描述要产生哪些事务；sequencer 管理事务供应与仲裁；driver 把事务变成接口时序。Monitor 独立观察真实接口行为，不能把 sequence 的计划直接当作已发生的输入。

**28. `item_done` 是否表示 DUT 已返回结果？**

- 不必然。它结束 driver 与 sequencer 的当前 item 协议，具体完成点由环境约定。若在输入握手后调用，DUT 输出仍可能待处理；测试必须等待 scoreboard 排空或定义其他可靠完成条件。

**29. Build、connect、run 和 check phase 怎样分工？**

- Build 创建和配置组件；connect 连接 TLM；run 执行耗时并发行为；check 检查结果与残留事务。Build 是 function，不能等时钟。不要认为各组件 run 按创建顺序串行执行。

**30. Objection 使用不当会发生什么？**

- 过早 drop 可能截断仍在运行的监视与比较，漏 drop 会导致测试挂住。应由明确的测试生命周期管理，在激励结束且在途事务处理完成后允许 phase 退出。固定延迟不能通用地替代排空条件。

**31. Factory 与 config_db 的区别？**

- Factory 解决“这次建哪一种对象”，例如把普通请求换成只生成边界值的请求；config_db 解决“把什么配置交给这个组件”，例如告诉 driver 使用哪个接口、等多久算超时。

- 类型替换要在对象创建前设好，且原代码要通过 factory 创建；配置读取失败则不能静默继续。

**32. Analysis port 为什么不能随意传一个反复修改的对象？**

- 广播可能把同一个句柄交给多个订阅者。生产者或某订阅者修改它，会影响其他消费者。

- 应新建/复制对象并约定只读；若订阅者需要等待，可先进入分析 FIFO，再在任务中处理，而不是在 write function 中耗时等待。

## 形式验证

**33. BMC 检查 12 拍没有失败，是否证明永远正确？**

- 不是，只能说在规定初态和假设下，前 12 步找不到反例。第 13 步或更远仍可能出错。归纳证明还要建立“起点成立，之后每一步都保持”的推理，成功后才能在该模型下推广到未来。

- 本章实际得到归纳 PASS，深度参数 12 并不是把设计只验证了 12 个仿真周期。

**34. Assume、assert、cover 的作用分别是什么？**

- Assume 限制环境，assert 定义要求，cover 寻找存在的轨迹。Cover PASS 不证明安全；assert PASS 也可能依赖过强假设。应同时审查假设和可达性，避免把实现责任写成环境承诺。

**35. 形式反例是否一定是 RTL bug？**

- 不一定。可能是设计错误，也可能是属性写错、复位模型不一致、缺少合法环境约束或黑盒抽象不合理。应读最早失败周期，按规格重放，再决定修 DUT、属性还是环境。

**36. 等价检查通过为何仍可能算错？**

- Gold 和 gate 可以实现同一个错误。等价检查关注两者是否一致，外部规格符合性需参考模型或属性检查。时序等价还依赖状态对应、初始化与模式约束，不能省略这些前提。

**37. W=4 的证明能直接推广到任意 W 吗？**

- 不能。具体参数证明只有该展开配置的状态空间。多个参数实例增加证据，但不是对任意参数的数学证明。本章属性证明 W=4，等价检查 W=8，其他宽度用仿真与结构检查。

## 门级、SDF 与 X

**38. 零延迟 GLS、SDF GLS 和 STA 各检查什么？**

- 零延迟 GLS 主要检查网表功能、连接与启动；SDF GLS 检查被激励到的延迟行为及工具支持的时序检查；STA 分析约束下的时序路径，不依赖功能向量。三者互补，不能仅靠 GLS PASS 宣布时序收敛。

**39. 计算题：SDF 为 `(2:3:4)` ns，选择 typ 如何确认反标有效？**

- 本例选择 3 ns，在输入变化后 2 ns 检查输出尚未变化，3.1 ns 检查已经变化，上升/下降各做一次。删除反标后默认 1 ns 导致过早变化并被检出。该窗口证明反标影响了行为，不是工艺库时序签核。

**40. 四态仿真的 X 等于芯片内部亚稳态吗？**

- 不等于。X 是数字模拟器对未知/冲突等情况的抽象，亚稳态是模拟电压过程。`if(X)` 可能乐观地选分支，门级也可能过度传播 X；应追查首个 X 来源并理解模型。

- 二态随机初始化、四态传播和物理 CDC 分析解决不同问题。
